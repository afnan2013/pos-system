How the POS API is built

One company, many food-and-beverage outlets. HQ (headquarters) runs the master menu and the reports; each outlet sells from its own menu and its own stock. This guide shows, one picture at a time, how the API behind it is put together, so you can find your way around the code on your first day.

Route→ Controller→ Service→ Repository→ pgtyped (generated)→ Postgres

Status: target design, 2026-11-25; each feature's spec confirms or changes its part. Nothing is built yet. The rulebook behind this page is docs/backend-design-patterns.md; the short version is .claude/rules/backend.md.

Chapter 1

The shape of a module

The API is split into modules, one per business area: auth, roles, users, outlets, menu, inventory, sales and reports. Every module has the same layers, and every request passes through them in the same order.

Each layer has one job and only knows the layer below it. That one rule is what keeps change small: a renamed column stops at the repository, a new JSON field stops at the controller, and the business rules in the middle do not move.

Controller

Translates HTTP

Parses the body, query and path with a zod schema, calls exactly one service method, maps the result to a response, and sends it.

Never runs SQL, decides a rule, writes an error body or logs.

Service

Holds the rules

Checks the user may act on this outlet, enforces the business rules, and decides which database changes happen together, in one transaction.

Never sees Express, status codes, JSON or database row types.

Repository

Talks to Postgres

Runs the generated query functions, turns each row into a model, and turns database errors into the app's own errors.

Never decides a rule, opens a transaction or knows HTTP.

The rule to remember: arrows only point down. A module reaches another module only through its service, never its repository. Shared plumbing (errors, logging, config, database, auth) lives in src/platform, which never imports a module.

Chapter 2

A request, end to end

A cashier taps Charge. The browser sends POST /api/v1/outlets/:outletId/sales to its own origin, so there is no CORS (cross-origin resource sharing) to set up. Caddy ends HTTPS and hands the request to the one app container, where it passes a short, fixed chain of middleware.

authenticate

Who are you?

Reads the ES256 token from the Authorization: Bearer header or the HttpOnly cookie (__Host-pos_at), checks the signature locally, and puts a Principal (user ID, outlet ID or none for HQ, permission keys) in the request context.

No token, bad token or expired token: 401.

requirePermission

May you do this?

requirePermission(Permission.SalesCreate) on the route. The token must hold at least one of the listed keys.

Missing key: 403.

assertOutletAccess

Here?

The service's first line. An outlet user may act only on their own outlet; an HQ user may act on any.

Another outlet's ID: 403, whether it exists or not.

What the middleware promise you
  • requestId keeps an incoming X-Request-Id only if it is 1 to 64 characters of [A-Za-z0-9._-], otherwise makes a UUIDv7, echoes it in the response, and opens the request context (AsyncLocalStorage) with a logger carrying it.
  • securityHeaders (proposed) is a small middleware in src/platform/http with no new dependency; it sets X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, X-Frame-Options: DENY and a strict Content-Security-Policy for the web app. Caddy adds Strict-Transport-Security.
  • requestLog writes exactly one line per request: method, route (the pattern, such as /api/v1/outlets/:outletId/sales), status, durationMs, bytes, requestId, plus userId and outletId once signed in.
  • express.json refuses bodies over 1 MB (413) and turns a parse error into one fixed message, because the parser's own text can quote the body, and the body may hold a password.
  • Health checks sit outside /api: /healthz (the process is up) and /readyz (the database answers).
Chapter 3

pgtyped: you write SQL, it writes the TypeScript

SQL written as a string inside TypeScript is invisible to the compiler: a typo in a column name, or a column someone renamed, compiles fine and fails when a customer hits that screen.

pgtyped fixes that. You write plain SQL in a .sql file next to the repository. pgtyped sends each statement to a real, migrated Postgres, asks it to describe the parameters and the result columns, and writes a typed function for it. Postgres itself does the checking. It is not an ORM: nothing clever happens at runtime, and you can read every generated line.

You write 
-- inventory.sql
/* @name DeductStock */
UPDATE pos.outlet_inventory
   SET quantity = quantity - :quantity!,
       updated_at = now()
 WHERE outlet_id = :outletId!
   AND menu_item_id = :menuItemId!
   AND quantity >= :quantity!
RETURNING quantity;
pgtyped writes 
// inventory.queries.ts (never edited)
export interface IDeductStockParams {
  quantity: number;
  outletId: string;
  menuItemId: string;
}
export interface IDeductStockResult {
  quantity: number;
}
export const deductStock =
  new PreparedQuery<IDeductStockParams,
    IDeductStockResult>(/* ... */);
// inventory.repository.ts: the name matches the statement
async deductStock(tx: Tx, outletId: string, menuItemId: string, quantity: number): Promise<number | null> {
  try {
    const [row] = await deductStock.run({ outletId, menuItemId, quantity }, tx);
    return row ? row.quantity : null;   // null: not enough stock
  } catch (err) {
    throw mapPgError(err);
  }
}
You changeWhat happens
Add a column in a migrationNothing breaks. Add it to the statements that should read it, regenerate, and the row type grows.
Rename base_price_minorRegenerating fails on every statement that names the old column; after fixing the SQL, tsc points at every mapper that read row.base_price_minor.
Typo in a statementPostgres refuses to describe it, so npm run db:generate fails before any code runs.
Forget to regenerateCI's drift check fails the pull request.

Two traps pgtyped cannot see: SUM() over a bigint returns numeric, which arrives as a string, so cast it back with ::bigint; and bigint money is parsed into a JavaScript number by a parser that refuses anything above Number.MAX_SAFE_INTEGER.

Chapter 4

Four shapes of data, two places they change

Follow HQ creating the menu item "Iced Latte". On its way in and out, the data takes four shapes, and it changes shape in exactly two places: the repository turns database rows into models, and the controller turns requests into inputs and models into responses. Those two conversions are buffers: a database change stops at the repository, an API change stops at the controller.

Why the row stays snake_case

pgtyped's column-renaming option is off, so a row reads row.base_price_minor and a model reads menuItem.basePriceMinor. A row can never pass for a model or a response by accident.

Why mappers list every field

The user model holds passwordHash. { ...user } in a mapper would send it. Writing each field by hand means a new field reaches the API only when someone decides it should.

Rules: never return a row or a model as JSON; never reuse a request DTO as a response; money is an integer in minor units everywhere (basePriceMinor: 35000); IDs are UUIDv7 strings; times are UTC, sent as ISO 8601.

Chapter 5

Errors: one path, one shape

Nobody in the chain writes an error response. Every layer just throws an AppError with a kind, Express 5 forwards it (thrown or rejected), and one errorHandler at the end turns every error, from anywhere, into the same RFC 7807 problem document. It also decides what gets logged, so each real failure is logged exactly once.

What the client receives

HTTP/1.1 409 Conflict
Content-Type: application/problem+json
Cache-Control: no-store
X-Request-Id: 0193b6f3-01bc-7d22-...

{
  "type": "/problems/conflict",
  "title": "Not enough stock for Iced Latte",
  "status": 409,
  "instance": "/api/v1/outlets/0193.../sales",
  "requestId": "0193b6f3-01bc-7d22-..."
}

A validation error adds "errors": { "items[1].quantity": "must be at least 1" }, keyed by the JSON names the client sent, so the web app can put each message under the right field.

Who does what with an error

  • repository passes every database error through mapPgError, and turns constraints that mean something (menu_items_sku_key) into area errors (ErrSkuTaken).
  • service throws area errors declared once in <thing>.ts.
  • controller throws from validate() and otherwise lets errors pass.
  • errorHandler writes the body and the log. Nothing else does either.

Outside the chain: an error in an un-awaited promise or a timer never reaches errorHandler. Those land in unhandledRejection or uncaughtException, which log at fatal and exit; Docker restarts the container. Every write is one transaction and every sale has an idempotency key, so a lost in-flight request is safe to retry.

Chapter 6

Transactions and the sale flow

A transaction makes several database changes happen together or not at all. The sale is the clearest case: deducting stock for three items, taking the next receipt number and saving the sale must all succeed, or none of them.

The service draws that boundary, because only it knows which changes belong together. One helper, withTx, hides BEGIN, COMMIT and ROLLBACK; the rollback is bounded to 5 seconds, so a dead connection can never hang a request.

Use case

No tx parameter

createSale(actor, outletId, input) opens the transaction with withTx(this.db, async (tx) => ...). Controllers call only use cases.

Step

Takes tx first

deductForSale(tx, outletId, lines) joins the caller's transaction and never opens one, even when it lives in another module.

Creating a sale, step by step

  1. 1
    Check accessThe route required sales.create; the service checks the cashier belongs to this outlet.
  2. 2
    Normalise the linesMerge duplicate items, reject a quantity below 1, then sort by menu_item_id. The sort fixes the order rows get locked in, so two sales can never deadlock each other.
  3. 3
    IdempotencyIf this Idempotency-Key already made a sale at this outlet, return that sale unchanged, with the same 201. A retried tap never charges twice. Two requests with the same key at the same moment: the second fails on the unique constraint, its transaction rolls back (receipt number included), and it re-reads and returns the first sale.
  4. 4
    Price the linesOne query over the outlet's assignments: the outlet's override, else the master price. An item that is not assigned, marked unavailable (is_available = false) or inactive rejects the whole sale with 409 ErrItemNotSellable.
  5. 5
    Deduct stock, one line at a time, in sorted orderUPDATE ... SET quantity = quantity - q WHERE ... AND quantity >= q RETURNING quantity. No row back means not enough stock: 409, and the rollback restores every earlier line.
  6. 6
    Take the receipt number lastUPDATE outlet_receipt_counters SET last_number = last_number + 1, updated_at = now() ... RETURNING last_number. The counter row stays locked for the shortest time; a rollback undoes the increment, so numbers never skip.
  7. 7
    Insert the sale, its lines and its stock movementsTotals computed in integer minor units. Insert sales, then sale_items (each line freezes the item name and unit price), then one stock_movements row per line (reason sale, negative change, sale_id), after the sale row because of the foreign key.
  8. 8
    Commit, respond 201The receipt is shown as DHK01-000042: the outlet code and the zero-padded number.
Never
  • SELECT MAX(receipt_number) + 1: two sales read the same maximum.
  • A Postgres sequence: not per outlet, and gaps on rollback.
  • SELECT quantity, then UPDATE: another sale slips in between.
  • Raising the isolation level as the fix.
  • A network call, password hash or token signing inside the transaction.
Always
  • Check and write in one conditional statement, with RETURNING.
  • Lock rows in a stable order (sorted by ID).
  • Keep transactions short; do slow work before or after.
  • One statement at a time on a transaction: no Promise.all on the same tx.
  • Test it with real concurrency: 50 sales at once must get receipts 1 to 50.
Chapter 7

Folders and wiring

Each module is one folder holding its routes, controller, DTOs, service, repository and SQL. Shared plumbing is written once in src/platform. Four small files at the top connect everything: main.ts reads settings and starts the server, services.ts builds every service once, routes.ts mounts one line per module, and app.ts puts the middleware in order.

api/
  migrations/             plain numbered SQL, never edited once applied
  src/
    main.ts               loadSettings, logger, pool, buildApp, serveUntilStopped
    app.ts                the middleware chain, in order
    services.ts           every repository and service, built once
    routes.ts             mountRoutes: one line per module
    platform/
      config/             loaders, Secret
      logger/             pino, request context, logger()
      errors/             AppError, kinds, kindOf
      http/               requestId, securityHeaders, requestLog, errorHandler, validate, respond
      db/                 createPool, withTx, mapPgError
      auth/               token signer, authenticate, requirePermission
      health/             /healthz, /readyz
    modules/sales/
      sale.ts             model, area errors
      sale.dto.ts         zod schemas, responses, mappers
      sale.routes.ts      paths and middleware
      sale.controller.ts
      sale.service.ts     createSale, listSales, getSale
      sale.repository.ts
      sale.sql            NextReceiptNumber, InsertSale, ...
      sale.queries.ts     generated by pgtyped
      dependencies.ts     MenuService, InventoryService
      sale.service.test.ts
    modules/              auth, roles, users, outlets, menu, inventory, reports
    cli/
      migrate.ts          migrations, then the permission sync
      seed.ts             demo outlets, menu, stock and users

Config

Read once at startup by four loaders. Every bad setting is reported at once, and the process stops before it listens. Secrets are wrapped in Secret, which prints xxxxx in logs and JSON.

Request context

AsyncLocalStorage carries the request ID, the logger and the signed-in user through every await, so logger() anywhere tags its line with them.

Permissions

Keys like sales.create live in modules/roles/permission.ts. npm run migrate copies them into the database, and HQ Admin always holds every HQ key.

Chapter 8

The rules

These are the decisions that are expensive to change later, made once now. Reviewers check every change against them; the full list with reasons is the review checklist at the end of docs/backend-design-patterns.md.

Four shapes, two conversionsRow to model in the repository; DTO to input and model to response in the controller.
Every input is validatedzod, .strict(); unknown fields are a 400; error keys are the JSON names.
One error writererrorHandler writes every error body as a problem document and logs each failure once.
Use cases open transactionsSteps take tx and join; no outside calls inside a transaction.
Concurrency by designConditional updates, stable lock order, receipt counter row last; READ COMMITTED stays.
Three access checksauthenticate and requirePermission on the route; assertOutletAccess in the service.
Money is an integerMinor units, bigint in Postgres, number in TypeScript, never a float.
Log IDs, not peoplepino JSON to stdout; never bodies, passwords, tokens, cookies or emails.
