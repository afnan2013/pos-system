Web app · UI blueprint

POS System UI Blueprint

Every page of the POS System web app: the HQ console where head office runs outlets, menu, prices, people and reports, and the outlet app where cashiers sell. For each page: who opens it, the permission it needs, what it shows, what people can do there, and how it looks while loading, when empty, on error and when the user has no access.

Status target design, 2026-11-25; each feature's spec confirms or changes its part Built nothing yet Engineering rules docs/frontend-engineering.md
Routes, endpoints and permission keys here are the agreed ones. Anything this page adds beyond them is tagged proposed and is confirmed at the spec gate of the feature that first needs it. A page that ends up different from this blueprint updates it in the same change.

Money

Stored and sent as integer minor units. Shown with two decimals and tabular figures: ৳1,240.00. One company currency, configured once as CURRENCY (default BDT, taka) proposed, with no currency column; formatted only in lib/money.ts.

Receipt numbers

Stored as an integer per outlet; shown as outlet code plus a six-digit number: DHK01-000124.

Time and language

English only. Times arrive in UTC and show in the device's time zone: 25 Nov 2026, 4:15 pm, or 4:15 pm for today.

Who uses it

Two kinds of user, never mixed. A user with no outlet is an HQ user and only ever sees the HQ console. A user tied to an outlet is an outlet user and only ever sees that outlet's app. What each one sees inside their area follows their role's permissions.

HQ users

Built-in role HQ Admin: every HQ permission plus sales.read and reports.read. HQ can create narrower HQ roles, for example a menu editor holding only menu.manage and menu.assign.

Device: a laptop or desktop, a few sessions a day. Dense tables are fine.

Outlet managers

Seeded role Outlet Manager: menu.read, inventory.read, inventory.adjust, sales.create, sales.read, reports.read. Sells at busy times, receives deliveries, fixes stock counts, checks the day's numbers.

Device: the counter tablet, or a laptop in the back office.

Cashiers

Seeded role Cashier: menu.read, sales.create, sales.read. Lives on the sell screen for the whole shift, with a queue waiting; reprints a receipt from the sales list now and then.

Device: a 10 to 11 inch tablet in landscape, or a laptop with a touch screen. Every control is sized for a finger.

App shells

Two shells, one per area. Menu entries and tabs the user cannot use are hidden, never greyed out. If the user cannot open an area's first page, its index route sends them to the first entry they can open proposed; with none at all, they land on /403.

Charging: what happens next

  • Idempotency key: one UUID per cart, made when the first item is added, sent in the Idempotency-Key header of POST /api/v1/outlets/:outletId/sales, and the same on every retry. A repeat with the same key returns the original sale, so a retry never sells twice.
  • The cart lives in the tab proposed: a reload, or signing in again after the hourly session ends, brings back the same cart and key.
  • Stock is capped in the cart: the stepper stops at the stock the menu reports, so "Only 4 left" shows before charging, not after.

Menu and prices · menu.assign

From GET /outlets/:outletId/menu. Assign item opens a dialog listing master items not yet assigned (from GET /menu-items, which menu.assign may read), with an optional outlet price and "Available". Change price sets the override; Use base price clears it (sent as null). The switch sets availability. All three use PUT /outlets/:outletId/menu/:menuItemId. Unassign uses DELETE behind a confirmation.

Stock · inventory.manage

From GET /outlets/:outletId/inventory: item, SKU, quantity, low-stock chip at 5 or fewer proposed, last change. Restock (positive amount, optional note) and Adjust (signed amount, note required proposed) post to .../inventory/:menuItemId/movements with reason restock or adjustment. A change below zero is refused and the API's message shows in the dialog.

Sales · sales.read

From GET /outlets/:outletId/sales, newest first, "Load more" with the API's cursor. Columns: receipt number, time, items, total. A row opens a side sheet with the sale's lines from GET /outlets/:outletId/sales/:saleId proposed, since there is no HQ route for one sale.

Unassign once sold. The API refuses to unassign an item that has sales or stock at the outlet (409). The dialog then reads "Cappuccino has sales or stock at Gulshan, so it can't be removed. Mark it unavailable instead?" with Mark unavailable as the primary button.

Page specs

One card per page. "Forbidden" describes what someone without the page's key sees if they reach the URL directly; the menus never link them there.

Public and system

Sign in

/login · public
Shows
Product name, email, password with a show toggle, Sign in. Centred card; works on a phone.
Actions
POST /auth/login sets the session cookie; then me refetches and the user goes to next if it starts with their own area (/hq or /outlet), else to their area's home.
Loading
Button spinner; button disabled while the request runs.
Error
One message for every failed sign-in: "Email or password is incorrect". 429: "Too many attempts. Wait a minute and try again." Network: "Can't reach the server."
Other
Someone already signed in is sent to their home. After the session ends mid-shift, the cashier signs in here and returns to the sell screen with the cart intact.

No access

/403 · signed in
For
A signed-in user whose role opens no page in their area.
Shows
"Your role ({role name}) doesn't give access to any page. Ask HQ to change your role." and Sign out.
Note
A missing key on one page is not this page: that shows the forbidden state inside the shell.

Not found

any unknown path
Shows
"This page doesn't exist." and a link to the user's home (or /login).
Note
A known route whose record is gone (/hq/menu/:menuItemId answering 404) shows a not-found state inside the shell instead.

Shared patterns

Built once in components/ and reused by every page.

Tables

  • Title, count and the primary button in the page header
  • Search and filters above; filters that matter live in the URL
  • Money and counts right-aligned with tabular figures
  • A whole row opens the record; a "···" menu holds row actions
  • Sticky header; under 640 px rows become stacked cards
  • Growing lists (sales) use "Load more" with the API cursor; master lists load whole

Forms

  • Label above input, hint below, error below the hint in red
  • Required fields marked; optional ones say "optional"
  • Money inputs show the ৳ prefix and accept "1250" or "1,250.50"
  • Server field errors land under their inputs
  • Primary action bottom right: "Create item", "Save changes"; disabled with a spinner while saving
  • Leaving with unsaved changes asks first proposed

Dialogs

  • Short tasks only: new outlet, new user, assign item, restock, change price
  • Title is the task; the primary button names the result
  • Escape and the close button cancel; focus returns to the opener
  • Errors show inside the dialog, which stays open
  • On phones, dialogs become bottom sheets

Confirmations

  • For deactivate, disable, unassign, delete, discard cart
  • Title asks the exact question: "Unassign Cappuccino from Gulshan?"
  • Body states the consequence in one sentence
  • The confirming button repeats the verb ("Unassign"), red when destructive; Cancel has focus

Toasts

  • After every successful write: "Saved", "Outlet DHK03 created"
  • For failures not tied to a field, with the API's title
  • Never for field errors (they are on the form) and never for the sale result (the receipt is the answer)
  • Bottom right on laptops, top centre on tablets, so the cart and Charge stay clear

States

  • Loading: skeletons in the page's real shape, after 150 ms proposed
  • Empty: what goes here, and the button that adds it if allowed
  • Error: what failed, Try again, request ID in small type
  • Forbidden: in the shell, never a sign-out
  • Status chips: green done or active, amber low or waiting, red sold out or failed, grey inactive; always text plus colour

Design system

One visual theme with light and dark mode, written as CSS variables under shadcn's token names, so every shadcn component picks it up with no per-component styling. This page is drawn with the same tokens, so switching your system to dark mode shows the dark values.

The idea. A work tool used all day: quiet neutrals, one ink-blue primary for what you can act on, and status colours kept for stock and outcomes. Blue never means a status, so "low stock" amber and "sold out" red are never confused with a button.

  • Mode: Light, Dark or System, chosen in the account menu and kept in the browser. A few lines in index.html set the dark class on <html> before React draws, so there is no flash of the wrong mode.
  • Rule: no colour value inside a component; only token classes (bg-primary, text-muted-foreground). Review checks it.
