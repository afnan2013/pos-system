POS System Design

A point of sale for one company that runs many food-and-beverage outlets. HQ owns the master menu, sets prices per outlet and watches sales; each outlet sells from its own menu and its own stock. One Express API and one React app run in one container, next to PostgreSQL, on a single EC2 server.

What the system does

Single company, many outlets: HQ sets up the menu and the outlets, outlets sell, HQ reads the numbers.

HQ

Users with no outlet. They manage outlets, the master menu, users and roles, restock any outlet, and read reports across every outlet in the HQ console at /hq.

Outlets

Each outlet has a short code such as DHK01, its own staff (managers and cashiers) and its own receipt numbers. Staff work in the outlet app at /outlet.

Menu

HQ creates master items with a base price, assigns them to outlets, and may override the price per outlet. An outlet sees only its assigned items.

Inventory

Stock is kept per outlet per item. Sales take it down, restocks and adjustments change it, and every change is logged. Stock never drops below zero.

Sales

A cashier rings up many items in one sale. One database transaction checks prices, takes stock and gives the next receipt number for that outlet, such as DHK01-000123.

Reports

Total revenue and sale count per outlet, and the top 5 items by quantity per outlet, for a date range. HQ sees every outlet; outlet staff see only their own.

How the pieces connect

Everything the user touches runs on one server. AWS around it provides the address, the disk, the secrets, the logs and the delivery path.

  1. Address. Route53 points pos.<domain> at an Elastic IP. The IP stays the same if the server is ever replaced.
  2. Caddy is the only container with open ports (80 and 443). It gets and renews the Let's Encrypt certificate by itself, adds Strict-Transport-Security (proposed), and forwards every request to app:3000.
  3. The app container runs Express. It answers /api/v1/*, /healthz and /readyz, and serves the built React app for every other path, so the browser and the API share one origin and need no CORS (cross-origin resource sharing) setup.
  4. Postgres runs as a container on the same server, reachable only on the internal Docker network. The API connects as pos_app (data access only); migrate runs first as migrator, and the app starts only if it succeeds.
  5. The data volume is a separate EBS (Elastic Block Store) disk mounted at /data, snapshotted daily. Replacing the server never loses data or the certificate.
  6. Delivery. On every push to main, after CI passes, GitHub Actions signs in to AWS through OIDC (OpenID Connect, so no AWS keys are stored), pushes the image tagged with the commit SHA to ECR, uploads the deploy/ files to S3, and runs deploy.sh <sha> on the server through SSM (Systems Manager). The script writes .env from Parameter Store, pulls, restarts, and fails the job if /readyz does not answer.
  7. No SSH. Port 22 is closed. Shell access is an SSM session.

Solid arrows carry traffic; dashed ones are DNS lookups, certificate renewal and the one-shot migration.

Inside the app

One TypeScript codebase per side. The API is split into layers that only call downward, and into eight business modules that each own their tables.

Layers, top to bottom

  1. Routes<thing>.routes.ts

    Path, method, and the middleware for that route: authenticate and requirePermission(...).

  2. Controllers<thing>.controller.ts

    Parse body, query and path with a zod .strict() schema, call one service use case, map the result to a response DTO (data transfer object).

    Never: SQL, business decisions, error bodies, logging.

  3. Services<thing>.service.ts

    Business rules, the outlet scope check, and the transaction boundary. A method without tx is a use case and opens the transaction with withTx; a method that takes tx is a step and joins it.

    Never: Express types, status codes, JSON, database row types.

  4. Repositories<thing>.repository.ts

    Call the generated queries with tx or the pool, map rows to models, map database errors with mapPgError.

    Never: business decisions, opening transactions, HTTP.

  5. pgtyped<thing>.sql → <thing>.queries.ts

    SQL lives in .sql files. pgtyped checks it against a migrated database and generates typed functions, committed and never edited. CI regenerates them and fails on any difference.

  6. PostgreSQL 18schema pos

    Foreign keys, unique constraints and checks refuse anything the services let slip.

Platform code shared by every module

src/platform/: config (zod-checked loaders, Secret), logger (pino, request context in AsyncLocalStorage), errors (AppError kinds), http (request ID, security headers, request log, validation, error handler), db (pool, withTx, mapPgError), auth (ES256 token signer, authenticate, requirePermission, outlet scope helper), health. Platform code never imports a module.

The web app

React 19 and Vite, one build. HQ users land on /hq, outlet users on /outlet. Server data lives in TanStack Query; the browser calls relative /api/v1/... paths and never holds the token, because the session is an HttpOnly cookie. Buttons a user cannot use are hidden, and the API still checks every rule.

Why we chose each thing

What we picked, why, and what we gave up for it.

Hosting

One EC2 server with containers, not managed services

Caddy, the app and Postgres run with Docker Compose on one t4g.small. It costs about $20 a month, is easy to reason about, and the same compose setup runs on a laptop. RDS, a load balancer and ECS would multiply the bill for traffic this system does not have.

Trade-off: one server is one point of failure, and we run Postgres ourselves. The separate data volume, daily snapshots and an automatic EC2 recover alarm limit the damage; moving to RDS is the first scaling step.

Edge

Caddy, not nginx or a managed gateway

Caddy gets and renews the HTTPS certificate on its own. The whole config is a few lines: the domain, compression, one header line for Strict-Transport-Security (proposed) and reverse_proxy app:3000. No certbot, no cron, no extra AWS service.

Trade-off: no edge rate limiting or web application firewall. Those belong to the scaling plan, not this build.

Web

Express serves the React build

One image holds the compiled API and the web build. The browser and the API share one origin, so there is no CORS, the cookie is a simple __Host- cookie, and one deploy ships both sides together.

Trade-off: static files come from Node, not a CDN (content delivery network). At this traffic that is invisible; a CDN can sit in front later without code changes.

Data access

pgtyped, not an ORM

The sale depends on exact SQL: conditional updates with RETURNING and a counter row lock. With pgtyped that SQL is written plainly and checked against the real schema, so a schema change turns into compile errors before anything ships.

Trade-off: more SQL written by hand, and generating types needs a migrated database (CI starts one). An ORM (object-relational mapper) would hide the locking behavior we most need to see.

Auth

Cookie JWT carrying permission keys

Sign-in sets an ES256-signed JWT (JSON Web Token) in an HttpOnly cookie that page scripts cannot read. It carries the user, the outlet and the permission keys, so each request is checked without a database lookup, and a route check is one set lookup.

Trade-off: the keys are a snapshot. A role change or a disabled user takes effect at the next sign-in, up to the 1-hour token life. There are no refresh tokens, so people sign in again when it expires.

Delivery

Terraform, OIDC and SSM

Every AWS resource is in Terraform, so the setup can be rebuilt from the repo. GitHub Actions assumes an AWS role through OIDC, limited to this repo's main branch, so no AWS keys are stored anywhere. Deploys run through SSM, so port 22 stays closed.

Trade-off: Terraform is applied by hand from a laptop, and a deploy restarts the app container in place, so a request may fail during the few seconds it takes. Rollback is deploying an older commit SHA.

Environments

One environment, prod

An assessment needs one working deployment. Changes are proven locally with docker compose up --build and in CI, where the tests start a real Postgres with testcontainers, before they reach main.

Trade-off: no staging copy to try a migration on real-shaped data. A second environment is a new Terraform state key and tfvars file away.

Three requests, end to end

Each step is tagged with where it runs.

  • Browser
  • Caddy
  • Express
  • Service
  • Postgres

1. A cashier signs in

POST /api/v1/auth/login, a public route.

  1. BrowserThe sign-in form posts email and password

    To /api/v1/auth/login on the same origin.

  2. CaddyHTTPS ends here

    Caddy forwards the request to app:3000.

  3. ExpressRequest ID, request log, JSON body

    No authenticate on this route. The controller parses the body with a strict zod schema; a bad body is a 400 problem with field errors.

  4. ServicePostgresFind the user and check the password

    Look up the user by lower-cased email, require status active, and verify the argon2id hash. A wrong email, a wrong password and a disabled account all get the same 401: "Invalid email or password".

  5. ServicePostgresLoad the role's permission keys and sign the token

    ES256 JWT with sub, outletId (null for HQ), perms, iat, exp (1 hour). Record last_sign_in_at.

  6. ExpressSet the cookie, return the user

    Set-Cookie: __Host-pos_at=...; HttpOnly; Secure; Path=/. The token itself never reaches JavaScript.

  7. BrowserLoad "me" and open the right app

    The app reads GET /api/v1/me. A cashier lands on the sell screen at /outlet; an HQ user lands on /hq.

2. A cashier creates a sale

POST /api/v1/outlets/:outletId/sales with an Idempotency-Key header. This is the path that must stay correct when many sales hit one outlet at once.

  1. BrowserCharge

    Body { items: [{ menuItemId, quantity }] }. The Idempotency-Key is a UUID made when the cart started and kept on every retry, so a lost response never sells twice.

  2. Expressauthenticate, requirePermission('sales.create'), validate

    Verify the cookie token and put the user (the "principal") in the request context. 403 without the key. The controller parses the body, path and header, then calls createSale.

  3. ServiceOutlet scope

    The cashier's outletId must equal the path's :outletId, otherwise 403.

  4. ServicePostgresOpen one transaction, check the key

    withTx, READ COMMITTED. If a sale with this key already exists for the outlet, return it unchanged with the same 201 and stop.

  5. ServiceMerge, then sort lines by menu_item_id

    Duplicate items become one line. The sort fixes the lock order, so two sales can never wait on each other's rows (no deadlock).

  6. PostgresPrice every line in one query

    Unit price is COALESCE(price_override_minor, base_price_minor). An item not assigned to the outlet, marked unavailable there (is_available = false), or inactive on the master menu rejects the whole sale with 409 ErrItemNotSellable.

  7. PostgresTake stock with a conditional update, line by line
    UPDATE pos.outlet_inventory
   SET quantity = quantity - :quantity, updated_at = now()
 WHERE outlet_id = :outletId AND menu_item_id = :menuItemId
   AND quantity >= :quantity
RETURNING quantity;

    No row back means not enough stock: 409 naming the item, and the rollback restores every earlier line. The check and the write are one statement, so no other sale can slip in between.

  8. PostgresTake the receipt number last
    UPDATE pos.outlet_receipt_counters
   SET last_number = last_number + 1, updated_at = now()
 WHERE outlet_id = :outletId
RETURNING last_number;

    The row lock makes sales at one outlet take numbers one after another, and is held only until commit. A rollback undoes the increment, so numbers have no gaps. Other outlets have their own row and never wait.

  9. PostgresInsert the sale, its lines and the stock movements

    Totals are computed in the service in integer minor units. Insert sales, then sale_items (each line freezes the item name and unit price), then one stock_movements row per line, with reason sale, a negative change and the sale's ID; the movements come after the sale row because of their foreign key to it.

  10. PostgresCommit

    If two requests with the same key raced past step 4, UNIQUE (outlet_id, idempotency_key) stops the second at insert; its whole transaction rolls back, receipt number included, and it re-reads and returns the first sale with 201.

  11. ExpressBrowser201 with the sale

    The receipt shows DHK01-000123: the outlet code plus the zero-padded number. The cart starts fresh with a new key.

Never MAX() + 1Two sales read the same maximum and collide.
Never a sequenceNot per outlet, and leaves gaps on rollback.
Never read, then write stockAnother sale fits between the read and the write.
Proven by tests50 concurrent sales get exactly 1..50; a race for the last units sells exactly what is there.

3. HQ opens the revenue report

GET /api/v1/reports/revenue-by-outlet?from&to, shown on the HQ overview at /hq.

  1. BrowserThe overview page asks for the report

    A TanStack Query hook calls the revenue report and, alongside it, GET /api/v1/reports/top-items for the top 5 items.

  2. Expressauthenticate, requirePermission('reports.read'), validate

    The controller parses from and to with zod; a bad date is a 400.

  3. ServiceOutlet scope decides the rows

    An HQ user (no outlet) gets every outlet. An outlet manager calling the same endpoint gets only their own outlet.

  4. PostgresOne read on the pool, no transaction

    Sum total_minor and count sales per outlet for the date range, joined to outlets for code and name. The index on sales (outlet_id, created_at) serves the range.

  5. ExpressJSON response

    One row per outlet: the outlet, revenue in minor units and sale count, in camelCase.

  6. BrowserRender

    Money is formatted only in lib/money.ts. The query result is cached, so returning to the page is instant while it refreshes.

Access control model

Two kinds of user, one role each, permission keys in the token, and a second check on the outlet in the service.

  1. Two kinds of user. A user with no outlet is an HQ user; a user tied to one outlet is outlet staff. Each user has exactly one role, and the role's scope must match the user's kind.
  2. Permission keys are named area.action and defined once in code (src/modules/roles/permission.ts). The migrate command syncs them into the permissions table; nobody edits that table by hand.
  3. A role holds keys of its own scope, plus the two any keys. The roles service refuses anything else, so an outlet role can never hold users.manage.
  4. Seeded roles. HQ Admin holds every HQ key and both any keys, and is locked so HQ cannot lock itself out. Outlet Manager holds every outlet and any key. Cashier holds menu.read, sales.create and sales.read. HQ can edit these two and create more.
  5. Two checks per request. The route checks the key; the service checks the outlet. reports.read on an HQ user means every outlet; on a manager it means their outlet only.

Data model at a glance

Twelve tables in the pos schema, simplified to their keys. Money is bigint minor units (_minor), times are timestamptz, IDs are UUIDv7 made by the API. Full detail lives in the database design document.

Outlets and menu

outlets
  • id PK
  • code UNIQUE e.g. DHK01
  • name · address · is_active
outlet_receipt_counters
  • outlet_id PK → outlets
  • last_number ≥ 0

Created with the outlet; one row lock per outlet.

menu_items
  • id PK
  • sku UNIQUE
  • name · category · base_price_minor ≥ 0 · is_active
outlet_menu_items
  • (outlet_id, menu_item_id) PK
  • → outlets → menu_items
  • price_override_minor (null = base) · is_available

Stock and sales

outlet_inventory
  • (outlet_id, menu_item_id) PK → outlet_menu_items
  • quantity ≥ 0

Created at 0 when the item is assigned.

stock_movements
  • id PK
  • outlet_id · menu_item_id · change
  • reason: sale | restock | adjustment
  • sale_id → sales, optional created_by → users

Append-only audit trail of every stock change.

sales
  • id PK outlet_id → outlets
  • receipt_number UNIQUE per outlet
  • idempotency_key UNIQUE per outlet
  • item_count · total_minor · created_by → users
sale_items
  • (sale_id, line_no) PK → sales
  • (outlet_id, menu_item_id) → outlet_menu_items
  • item_name · unit_price_minor (frozen)
  • quantity > 0 · line_total_minor

People and access

users
  • id PK email UNIQUE, any case
  • outlet_id → outlets, null = HQ
  • role_id → roles
  • password_hash · status: active | disabled
roles
  • id PK name UNIQUE
  • scope: hq | outlet · is_system
permissions
  • key PK e.g. sales.create
  • scope: hq | outlet | any

Synced from code by the migrate command.

role_permissions
  • (role_id, permission_key) PK
  • → roles → permissions

How they relate

  • Outlets and the master menu meet in outlet_menu_items: one row per item assigned to an outlet, with an optional price override. Effective price is the override, else the base price.
  • Each assignment has one stock row in outlet_inventory, and every change to it (sale, restock, adjustment) adds a stock_movements row.
  • An outlet has many sales, a sale has many sale_items. Lines freeze the item name and price, so editing the menu never rewrites history. sale_items copies outlet_id so the top-items report reads one index.
  • Each outlet has one counter row in outlet_receipt_counters, the source of its receipt numbers.
  • Users point to one role and, for outlet staff, one outlet. Roles get permissions through role_permissions. Sales and stock movements record who made them.

How it grows

The brief's target is 10 outlets and 100,000 sales a month. That load is small for Postgres, so the first steps are about safety and reporting speed, not raw capacity. The full scaling plan, the path to microservices and the offline POS strategy live in the architecture document (docs/architecture.md).

Back-of-envelope numbers, assuming 3 lines per sale and a busy hour of 4 times the average (proposed):

~3,300sales a day across 10 outlets
~700,000new rows a month (sales, lines, stock movements)
~0.3 / ssales at the busiest hour, each about 10 statements
~3 GBa year of data and indexes; the volume holds 20 GB
  1. Keep the shape, watch the queries. The indexes on sales (outlet_id, created_at) and sale_items (outlet_id, menu_item_id) already match the reports. Receipt counters are per outlet, so outlets never wait on each other.
  2. Move Postgres to RDS with Multi-AZ and point-in-time recovery. The app image does not change; only the connection settings do.
  3. Pre-compute reports with a daily summary per outlet and item, so reports stop scanning raw sales as history grows (proposed). Later, a read replica serves reports.
  4. Two or more app servers behind a load balancer. Tokens are stateless, so any server can answer any request.
  5. Split services where it pays. Reports first, as a read-only consumer; the sale transaction stays together with inventory.

Still to decide

Open questions, each settled in the spec of the feature it touches.

  • Migration runner libraryChosen in the foundation spec; migrations stay plain numbered SQL either way.
  • Session length at the tillA 1-hour token with no refresh signs a cashier out mid-shift. Longer tokens for outlet roles, or a refresh flow?
  • Revoking access earlyA disabled user or changed role keeps the old token until it expires. Is up to 1 hour acceptable?
  • Report day boundariesAre from and to UTC instants or the outlet's local day, and is to inclusive?
  • Sign-in rate limitingNo edge limit in this build; an in-app limit on /auth/login would use the rate_limited error kind.
  • Database TLS on the host networkConnections never leave the Docker network, so TLS is relaxed for db; recorded as an ADR (architecture decision record) in the foundation.
  • Backups beyond snapshotsDaily EBS snapshots only. Add a nightly pg_dump to S3 as a copy off the volume?
  • Alarm notificationsThe EC2 recover alarm acts on its own but tells no one. Email or chat alerts?
  • Voids and refundsNot in scope. A refund would add a stock movement and a negative sale, never edit a sale.
