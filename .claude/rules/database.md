# Database rules

Full design: `docs/database-design.md`.

## Schema conventions

- One schema, `pos`, owned by the `migrator` role; the API connects as `pos_app`, which has data access only (no DDL), and only the rights each table needs (sales history is insert-only).
- `pos_app` timeouts are set on the role by the init script: `statement_timeout` 5s, `lock_timeout` 2s, `idle_in_transaction_session_timeout` 10s.
- Tables `snake_case` and plural; columns `snake_case`.
- Primary keys are `id uuid`, generated by the API as UUIDv7 (time-ordered, index-friendly).
- Money columns are `bigint` minor units ending in `_minor` (`price_minor`, `total_minor`).
- Times are `timestamptz`; every table has `created_at`, and mutable tables also have `updated_at`.
- `bigint` arrives in JavaScript as `number` through a `pg` type parser that refuses unsafe integers; pgtyped maps `int8` to `number` to match.
- Status-like values are `text` with a `CHECK (... IN (...))`, not Postgres enums.
- Copy data only as frozen history: a sale line stores the unit price and item name at the time of sale; everything else joins live data.

## Constraints are the last line of defence

The service enforces every rule first; the database refuses anything that slips past.

- Every relationship is a `REFERENCES` foreign key, with `ON DELETE` chosen on purpose (usually `RESTRICT`).
- `CHECK (quantity >= 0)` on stock; `CHECK (price_minor >= 0)` on prices; `CHECK (quantity > 0)` on sale lines.
- Assignments and inventory are keyed by `(outlet_id, menu_item_id)`; sale lines reference the assignment, so only assigned items can be sold.
- `UNIQUE (outlet_id, receipt_number)` on sales; `UNIQUE (outlet_id, idempotency_key)` where the key is present.
- Unique business identifiers (outlet code, menu item SKU, user email) get a unique constraint or unique index.

## Indexes

- Every foreign key column used in a join or filter is indexed (Postgres does not do it automatically).
- Index the real query shapes: sales by `(outlet_id, created_at)` for date ranges and `(outlet_id, receipt_number)` for the sales list; sale lines by `(outlet_id, menu_item_id)` for top-item reports (the primary key `(sale_id, line_no)` serves reading one sale).
- Indexes we name ourselves use `ix_<table>_<columns>`, unique ones `ux_<table>_<columns>`; inline constraints keep Postgres's automatic names.
- Every new index states which query it serves, in the migration's commit message.

## Migrations

- Plain SQL files in `api/migrations/`, numbered, applied in order by `npm run migrate` as `migrator`.
- Never edit a migration that has been applied anywhere; add a new one.
- Expand and contract for breaking changes: add the new shape, move readers and writers, then remove the old one in a later migration.
- New indexes on tables that already hold data use `CREATE INDEX CONCURRENTLY` in their own migration.
- Each migration grants what `pos_app` needs on new tables.

## pgtyped

- SQL lives only in the module's `<thing>.sql` file; no SQL strings in TypeScript, except infrastructure SQL inside `src/platform/db`.
- Query names are `VerbNoun` and say what they do: `GetMenuItem`, `ListOutletMenu`, `DeductStock`, `NextReceiptNumber`.
- Parameters that must be present are marked required (`:outletId!`); nullable result columns that are never null get a not-null hint.
- Conditional updates use `RETURNING` so the repository can tell "0 rows changed" from success.
- Aggregates over money are cast back (`SUM(total_minor)::bigint`), because `SUM(bigint)` returns `numeric`, which arrives as a string.
- List columns explicitly; no `SELECT *` or `RETURNING *`.
- After any migration: `npm run migrate`, then `npm run db:generate`, then fix every compile error it causes.
- Generated `*.queries.ts` files are committed and never edited; CI regenerates them and fails on any difference.

## Repositories

- Take `tx` or the pool as the first argument; never open a transaction.
- Map every row to a model with a hand-written `toX(row)` function next to the repository.
- Pass database errors through `mapPgError`; translate a foreign-key violation on delete ("still referenced") into the area's own error.
- Return `null` for "not found" on single reads; the service decides whether that is an error.
